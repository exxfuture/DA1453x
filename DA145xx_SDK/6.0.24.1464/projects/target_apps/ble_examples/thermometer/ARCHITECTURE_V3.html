Thermometer — System Architecture v3

Revision of ARCHITECTURE_V2.html (v2) to use a backend language the team already has deep expertise in, and a more widely-adopted web frontend framework. Requirements are unchanged. This document replaces the backend language and the web UI framework, keeps every v2 infrastructure decision that doesn't depend on either (broker, storage, identity, OTA strategy, deferred-complexity triggers), and is explicit about the tradeoffs behind both swaps.

Decision up front: backend platform services move from Go to Java 21+ LTS / Spring Boot 3.2+ with virtual threads. The web app moves from Angular to React + TypeScript + Vite, still wrapped in Capacitor for the shared web/Android/iOS codebase. The optional Raspberry Pi gateway binary stays Go — it's a different deployment target (a resource-constrained edge device), not a second backend language competing with the first. Reasoning for all three calls is in §2–3.
This architecture has a working implementation in the sibling folders (backend/, fe/, mobile/, gateway/, deploy/, docker-compose.yml) — runnable locally with docker compose up, no physical thermometer required (a simulator stands in for the device). See §16 for exactly what's real vs. scaffolded, or jump straight to ../README.md's "Platform" section for the quick start.

2. Backend language decision: Java vs. Go

2.1 The honest tradeoff table

DimensionGo (v2's pick)Java 21 + Spring Boot 3.2 (v3's pick)
Team fit New language/ecosystem for a Java-strong team — real ramp-up cost, ongoing "translate the idiom" tax on every feature. Direct reuse of existing expertise. Faster delivery, better code review quality, easier hiring/onboarding against the stack the team already knows.
Idle memory / cold start ~10–30 MB idle, near-instant start — genuinely excellent, single static binary. Plain JVM mode: ~150–300 MB idle, 1–3 s cold start. With GraalVM Native Image (Spring Boot 3 AOT support, opt-in): tens of MB, tens of milliseconds — closes most of the gap.
Concurrency model for I/O-bound MQTT/DB workloads Goroutines — cheap, built-in, simple mental model. Virtual threads (stable since Java 21, "Project Loom"): write ordinary blocking-style code (a thread per MQTT message/session, blocking JDBC calls) and the JVM schedules millions of them cheaply. Gets Go-like scalability without reactive/WebFlux complexity — the team keeps writing code the way it already knows how.
Ecosystem fit with the rest of the stack Standalone — no particular synergy with Keycloak or (if ever adopted) hawkBit. Keycloak is itself a Quarkus/Java application, and hawkBit (deferred per §14, adopt-when-triggered) is Spring Boot. An all-Java platform means one JVM tuning/monitoring playbook across every server-side component, and zero new-language cost the day hawkBit is actually adopted.
Libraries for this domain Solid, minimal (MQTT client, JWT, JSON schema) — you assemble more yourself. Mature, batteries-included: Spring Data JPA/JDBC for Postgres+Timescale, Spring Security + OAuth2 Resource Server for Keycloak-issued JWTs (this is exactly what Spring Security is built for), Spring Boot Actuator + Micrometer for Prometheus metrics out of the box, HiveMQ MQTT Client (Apache-2.0) for the broker connection.
Testing ecosystem Good, but Testcontainers (used to spin up real Postgres/Mosquitto/ Keycloak in CI) is a Java-native project — support elsewhere is thinner. Testcontainers is at its best here — deepest integration, largest module catalog, first-class JUnit 5 support.
Build/CI complexity Trivial — go build, tiny static binary, fast every time. Plain JVM mode: trivial (standard mvn package/./gradlew build). Native Image mode: a real added cost — multi-stage GraalVM/Mandrel builder image, native compilation adds minutes to CI, and some libraries need reflection hints (Quarkus/Spring curate extensions to minimize this, but it's not zero-risk). Treat as opt-in, not default.

2.2 Where the v2 cost argument was weaker than it looked

v2 picked Go partly on hosting cost. Revisited honestly: at the actual VPS sizes in play for MVP/Growth (2–4 GB RAM), a Spring Boot service's extra ~150–250 MB over a Go binary is real but is not the constraint that determines whether the box is big enough — disk, connection limits and CPU headroom matter more at this scale, and the difference is a rounding error against a 4 GB box running four or five services. The cost argument for Go was real but secondary; team velocity was the load-bearing factor all along, and it now points the other way.

2.3 The decision

  • Java 21+ LTS, Spring Boot 3.2+ for the API and ingest services. Spring Boot over Quarkus specifically because "Java expertise" in industry overwhelmingly means Spring-flavored Java — this maximizes reuse of what the team already knows, at the cost of a somewhat higher idle footprint than Quarkus would give by default. (Quarkus remains a reasonable alternative if the team is specifically comfortable with it — it's built for exactly this footprint/startup axis — but it's not the default here.)
  • Virtual threads enabled (spring.threads.virtual.enabled=true) so ingest/API code stays simple, blocking-style Java — no reactive rewrite needed to get high concurrency out of I/O-bound MQTT and DB work.
  • GraalVM Native Image is an explicit, opt-in upgrade, not a day-one requirement — adopt it once the team is comfortable with the added build complexity, to close the remaining footprint/cold-start gap with Go. Until then, plain JVM mode is entirely adequate; it just costs a slightly bigger VPS tier (§12).
  • Go stays exactly where it already made sense on its own merits: the optional Raspberry Pi/SBC gateway collector binary. This isn't a "some services in Go" hybrid — it's recognizing that an edge device and a data-center container are different problems, and Go is still the better tool for the former regardless of what the platform backend uses.

3. Frontend framework decision: React vs. alternatives

3.1 Web app: React + TypeScript + Vite

OptionVerdictReasoning
React + Vite (chosen) ✅ Selected Widest talent pool and ecosystem of any option evaluated across v1–v3. Vite is the current standard React toolchain (superseded Create React App): fast dev server, fast builds, no unnecessary runtime. The app is an authenticated SPA dashboard — no page needs to be indexed or server-rendered.
Next.js (React, with SSR/SSG) ❌ Not chosen Its core value — server rendering and SEO — doesn't apply to a logged-in health dashboard, and cannot apply to the one screen that matters most: Web Bluetooth is a browser-only API and can never be server-rendered. Adopting Next.js here would mean operating an extra Node server runtime for no benefit this project can use.
Angular (kept as-is) ❌ Not chosen (this revision) The existing FE works and its BLE/IEEE 11073 decode logic is already correct and tested (see migration note, §3.3) — but Angular has a smaller hiring pool and ecosystem than React, which is the specific gap this revision addresses.

3.2 Supporting stack for the React app

  • TanStack Query for all server-state (REST history queries, cache invalidation on live measurement events) — the standard, widely-adopted data-fetching layer for React today.
  • Zustand for local/UI state (selected device, BLE connection status) — smaller and simpler than Redux for a project this size, and currently the more common default for new React codebases.
  • React Router for navigation — the largest install base of any React router, the safe default. (TanStack Router is a fully type-safe alternative worth a look if the team wants tighter integration with TanStack Query, but isn't necessary here.)
  • Tailwind CSS + a bespoke design-token/component kit (not shadcn/ui) for the dashboard UI — a "Pine & Ember" health-oriented visual language (light + dark themes, a 5-tier temperature-status color scale, Fraunces/Public Sans/IBM Plex Mono type, lucide-react icons) with its own Button/Card/Input/Badge/ StatCard/Table/Alert primitives in fe/src/components/ui/, chosen over shadcn's generic defaults so the product reads as distinctively health-focused rather than generic SaaS, while keeping the same "accessible primitives on Tailwind" approach shadcn would have given (WCAG AA contrast, focus-visible states, 44px touch targets). See fe/README.md "Design system" for the full token/component inventory.

3.3 Mobile: Capacitor stays, now wrapping React

The v1/v2 case for Capacitor was never "because Angular" — it was "one codebase, one set of UI components and one BleTransport abstraction, shipped to web, Android and iOS." That case is framework-agnostic: Capacitor wraps any web app, so swapping the UI layer to React changes nothing about the strategy, only what's inside the wrapper.

OptionUI codebases to maintainVerdict
Capacitor + React (chosen) One (the React web app, rendered in a WebView on mobile) ✅ Same rationale as v1/v2, React swapped in for Angular.
React Native Two (React DOM components for web, React Native components for mobile) sharing only business logic (hooks, BLE codec, API client) via a monorepo package Considered, not chosen as the default. It gives a more natively-idiomatic mobile UI and a large ecosystem (react-native-ble-plx is mature) — a legitimate option if the team later decides native look-and-feel matters enough to justify maintaining two UI layers instead of one. For a data/BLE dashboard app, that tradeoff doesn't pay for itself today.

3.4 Migration cost — be honest about it

This is a real rewrite, not a free upgrade. The existing Angular FE already correctly decodes the IEEE 11073 FLOAT format (0.01 °C resolution) — a detail the vendor's own SmartBond app gets wrong (see README.md, "Temperature encoding"). Before building new UI, port the pure, framework-agnostic pieces first — IEEE 11073 decode, HTP characteristic parsing, CRC/validation logic — as plain TypeScript with unit tests ported alongside them, verified against the existing Angular tests. Only then build the new React components on top. This avoids silently reintroducing a decode bug the project has already solved once.

9. Identity, profiles and access control (v3)

Roles, consent-link model and row-level-security enforcement are unchanged from v2 §8. The decision to keep Keycloak (v2 §8.1) is, if anything, reinforced by the language choice: Keycloak already runs on the JVM (Quarkus), so an all-Java platform means every server-side component — API, ingest, identity, and hawkBit if/when it's adopted — shares one runtime family, one GC/monitoring playbook, and one on-call mental model. Gateway JWT-first authentication (v2 §8.2) is unchanged; Spring Security's OAuth2 Resource Server support validates Keycloak-issued and gateway-issued JWTs with standard, well-trodden configuration rather than hand-rolled verification.

Implementation note (FR-4/FR-5, now live): Keycloak deliberately holds no relationship data — no groups, no user attributes, nothing that could express "doctor X treats patient Y." That was always going to live in the backend's own users/consent_links tables, and it does: security/CurrentUserService JIT-provisions/re-syncs a local users row from the JWT on every request (first authenticated call creates it), and every controller does an explicit role check against the resolved identity rather than Spring's @PreAuthorize/hasRole() — the local profile's fully-open filter chain still populates an anonymous authentication with ROLE_ANONYMOUS under the hood, which would make any hasRole(...) annotation reject local curl testing entirely. Per-device ownership exclusivity (a device has one owner at a time) is enforced in-app on claim; a customer may own multiple devices — an earlier one-device-per-customer cap (DB-enforced by a partial unique index) was tried and then deliberately dropped once it turned out to block the ordinary case of claiming a second device you're already connected to. See backend/README.md "Roles & identity" for the full endpoint table.

Consent-scoped sub-resources (added after the initial v3 build): the patient→doctor consent link is no longer only a gate on measurement history. It now governs a small family of resources that hang off a patient: alert thresholds (a per-user tier scale with whole-row precedence doctor_override → self → system → built-in fallback), derived temperature events (threshold-crossing episodes computed on read from the measurements hypertable — no events table, so a threshold change re-tiers history for free), reading annotations (customer-authored, readable by anyone who may read the readings), and care notes (doctor-authored and doctor-private — consent flows patient→doctor only, so there is no channel through which a patient-visible clinical note would be delivered; admin gets a read-only compliance view). The ownership/consent decision itself is one shared component (security/DeviceAccessGuard) rather than a check re-implemented per controller, which is what keeps four resources from drifting into four subtly different access rules.

One deliberate exception to "no @PreAuthorize": /actuator/**. Spring Security resolves those paths before any controller exists, so the in-controller convention above cannot reach them — which is why, until an audit caught it, /actuator/info and /actuator/prometheus were readable by any authenticated user rather than admins only. A Keycloak realm_access.roles → ROLE_* JWT converter now exists, scoped only to the secured filter chain, purely so hasRole("ADMIN") can gate the actuator (with /actuator/health left open for probes). The application's own endpoints are unchanged, and the local profile's open chain is untouched.

10. Firmware update pipeline (v3)

Unchanged in shape from v2 §9: DIY rollout tables in Postgres + MinIO for images/deltas, phased group percentages with abort thresholds, signed and diffed images from CI. The only change is that the rollout-evaluation logic is now a Spring Boot service instead of a Go one — and the future upgrade trigger (adopt hawkBit once rollout policy genuinely needs a dedicated engine) now comes with zero new-language cost, since hawkBit is itself Spring Boot.

11. Security model

Unchanged from v2 §10 in every particular — TLS everywhere, JWT-first collector/gateway auth with optional mTLS, broker-enforced topic ACLs for the live feed, encrypted data at rest, signed and now-diffed firmware, append-only audit log, rate limiting and schema validation at ingest. None of it is specific to Go or Java.

Implementation note (what of this is actually live): schema validation at ingest, the append-only audit log and JWT-first API authentication shipped with the initial v3 build. A later audit closed three gaps and added one signal:

  • Rate limiting is now real — Bucket4j token buckets in Caffeine, keyed by caller IP, applied by a servlet filter that runs ahead of Spring Security so floods cost no JWT validation or database work. A blanket budget plus a much tighter one on the OTA collector endpoints. State is per-instance in-memory, which is correct for the single-instance compose deployment and is the thing to revisit when replicas appear — N instances silently mean limit × N, not a distributed limit.
  • The OTA collector endpoints are no longer unauthenticated. They were permitAll() with no compensating check, so anyone could enumerate firmware metadata by BD address or POST fabricated install failures until a rollout tripped its own auto-abort threshold. They now require a shared X-Device-Token (constant-time compared). This is explicitly the MVP shape of the model described above, not its end state: the model calls for JWT-first collector auth with optional mTLS, and a fleet-wide shared secret is neither — one extraction compromises the fleet and revocation is all-or-nothing. Per-device credentials need provisioning infrastructure that doesn't exist yet (tracked in proposals.md 10.1); the tight collector rate-limit bucket is the compensating control until then.
  • The actuator lockdown described in §9.
  • Denied requests are now audited (access.denied rows on every 403), which is what makes an operator-facing security-anomaly view possible at all — the audit log previously recorded only successful state changes, so "someone is probing device ids" left no trace.

Still not implemented from the model: TLS (the local stack is plain HTTP), broker-enforced topic ACLs (Mosquitto runs anonymous for local dev), encryption at rest, and firmware signing.

13. Testing strategy (new in v3)

Called out explicitly because the language choice makes it unusually strong here:

  • Testcontainers (JUnit 5 integration) spins up real Postgres+TimescaleDB, Mosquitto and Keycloak containers per test run — the ingest/API tests run against the actual dependencies, not mocks, catching integration issues (schema drift, broker ACL misconfiguration, token validation edge cases) that unit tests alone would miss.
  • Contract tests for the message envelope (JSON Schema validation) run identically whether the producer is the Angular-derived codec port, the React web app, the Capacitor mobile app, or the Go gateway binary — one schema, four producers, tested once.
  • Firmware-side host-tested codec logic (tests/run_tests.sh, already in place per README.md) is unaffected by any of this — it stays as-is.

14. Deployment, operations and cost (v3)

  • Packaging: unchanged — OCI containers, docker-compose for MVP, k3s from Growth on. Spring Boot images built on an arm64 JRE base (or a GraalVM/Mandrel builder stage if Native Image is adopted).
  • Observability: unchanged — Grafana Alloy per host, self-hosted Prometheus/Loki/Grafana. Spring Boot Actuator + Micrometer expose Prometheus-format metrics natively, one dependency, no manual instrumentation needed.
  • Backups: unchanged — pgBackRest + WAL archiving, MinIO versioned buckets replicated off-site with restic.
  • CI/CD: platform lane now builds/tests a Maven or Gradle project (Testcontainers-backed integration tests, §13) instead of a Go module; firmware lane (delta image generation + signing) is unchanged.
  • Cost sketch: MVP ≈ one ~€10–18/month arm64 VPS in plain-JVM mode (or ~€5–8/month at v2-parity with Native Image adopted) + domain. Growth and Scale tiers are unaffected by the language choice — the same handful of dedicated servers as v2 once EMQX/JetStream are actually justified.

Doctor UI (Patients page) and admin UI (Relationships tab) both ship. Fine-grained scope (e.g. "vitals only") remains schema-only/unused — full access is implied by an active link. The link now also gates a family of consent-scoped sub-resources — alert thresholds, derived temperature events, reading annotations and (doctor-private) care notes — through one shared DeviceAccessGuard rather than a per-controller re-implementation; see §9. Admin additionally gets a consent-integrity scan (links pointing at deleted accounts, doctors holding an implausible number of links), which is the kind of data-quality problem that is invisible when links can only be paged through one screen at a time.
FR-5 implemented Three roles (customer/doctor/admin) enforced end-to-end: a local users table is JIT-provisioned from the Keycloak JWT on every request (security/CurrentUserService), and every controller does an explicit role check against it — deliberately not Spring's @PreAuthorize/hasRole(), since the local profile's open filter chain would otherwise reject every unauthenticated dev request via ROLE_ANONYMOUS (see backend/README.md "Roles & identity"). Device claiming is customer-only; a device can only have one owner at a time but a customer may claim several — with a dedicated admin force-release/edit path instead of admin competing for ownership. The rollout-creation endpoint now has its admin-only guard. Two later refinements: /actuator/** is the one path that does use hasRole("ADMIN"), because Spring resolves it before any controller (§9); and admin's role-change endpoint deliberately edits only the local mirror — CurrentUserService re-syncs role from the JWT at next login, so it is an audited correction tool for a drifted mirror, not a role editor. A real one needs the Keycloak Admin API (proposals.md 10.4).
FR-6 partially implemented DIY rollout targeting (percentage groups, version comparison, auto-abort on error threshold) is implemented and unit-tested, and now has an operator surface: a paginated admin rollout list with batched installed/failed/pending progress counts, a detail view with the per-device target table, and an alert when the failure rate has passed the rollout's own abort threshold. The two collector endpoints are authenticated (shared X-Device-Token) and rate-limited — see §11 for why that is the MVP shape rather than the end state. Not implemented: actual firmware image storage in MinIO, delta-image generation in CI, and the collector-side SUOTA download/apply step — the firmware itself also doesn't have SUOTA yet (tracked as proposals.md item 3.4).
FR-7 implemented React + Vite web app: Web Bluetooth connect, correct IEEE-11073 decode (ported and tested against the Angular app's proven logic), direct MQTT/WSS live feed (subscribed and rendered), a role-aware nav/routing layer (customer/doctor/admin see different pages), a charted dashboard (recharts, 1h/24h/7d range) replacing the old bare-table history view, a device fleet browser (claim/ release), a settings page (profile + doctor-consent management), a doctor patient list with a fleet-overview dashboard (stats, fever alerts, search/filter/sort, per-patient sparklines — backed by GET /api/doctor/patients/summary), an admin console (users/devices/relationships), and a working login against Keycloak. The login is the real production flow: standard OAuth2 Authorization Code + PKCE, redirecting into Keycloak's own hosted login page (fe/src/auth/oidc.ts, oidc-client-ts/react-oidc-context) rather than a credential form owned by this app — thermometer-web's directAccessGrantsEnabled is off. The session persists across reloads (refresh token in localStorage, proactively renewed before the access token expires) and lasts until Keycloak's SSO session actually ends — expiry, explicit logout, or an admin revoking the session — not merely until the tab is refreshed; logout ends the Keycloak SSO session server-side too. Password change (Settings page → "Change password") and "Forgot password?" are both handled entirely by Keycloak's own hosted UI as well — a redirect into its kc_action=UPDATE_PASSWORD required-action form and its built-in resetPasswordAllowed flow respectively, with the realm's password policy enforced by Keycloak itself. No password, current or new, ever reaches this app's own code in any of the three flows; the backend has no password-related endpoint at all. Reset emails are real and inspectable via a local mailpit SMTP catcher rather than being a theoretical capability — see backend/README.md "Authentication" and §16.3 below for how this was verified. A SimulatedBluetoothTransport (third BleTransport implementation alongside Web Bluetooth and native) makes the entire app testable with no physical thermometer and no Web Bluetooth support required — see §16.3.

Later feature pass (thirty capabilities, ten per role). The chart was rewritten to scroll horizontally through time (a Brush plus always-present step buttons) with a vertical axis recomputed from the visible window, so a fever spike reads as a spike instead of being flattened by a fixed full-range axis — the window is held as timestamps and re-resolved to indices each render, because the 5 s rolling refetch makes index 0 a different instant on every tick. Customers gained fever-episode history, a trend digest, multi-device comparison, CSV export, per-reading annotations, personal alert thresholds, device-health badges, consent-access transparency and an onboarding checklist; doctors gained risk ranking, a fleet-wide episode feed, variability/trend indicators, a printable clinical report, care notes, multi-patient comparison, per-patient threshold overrides and their own audit trail; admin gained deep-linkable /admin/* sub-routes covering ingest health, device inventory, rollout progress, user growth and search, a filterable audit log with a security-anomaly view, consent-integrity warnings, retention insight and the system-default thresholds. No new design tokens were needed for any of it, which is the practical evidence the token system was already sound; a grep audit found exactly one ad-hoc color in the whole app, and fixed it. The production bundle is currently a single ~1.26 MB chunk with no route splitting (proposals.md 10.3). Per-page detail is in fe/README.md's implementation-status tables.
FR-8 partially implemented Capacitor project + native BLE transport implemented and type-checked against the real plugin API; Android/iOS platform scaffolding verified to generate and (for Android) resolve Gradle / (for iOS) run pod install correctly in this environment. Not verified: an actual on-device/simulator build (this environment has Xcode but no installed Simulator runtime, and a JDK too new for the auto-downloaded Gradle version) — see mobile/README.md for the exact verification boundary.
FR-9 partially implemented measurement_types registry table exists; the ingest service's scalar-extraction switch already handles temperature/humidity/battery. Only temperature actually flows through a device/FE today — adding a second type end-to-end (the extensibility proof from the roadmap) is still open. Battery is the concrete instance of this gap: the firmware polls the Battery Service every 60 s, but no collector — gateway, browser transport or simulator — ever publishes a type=battery envelope, so the customer device-health widget shipped with staleness only and no battery trend. Closing it is collector work; the backend and schema need no change (proposals.md 10.2), which also makes it the cheapest way to land the second-measurement-type proof.
NFR-1…6 holds at MVP scale Verified at the scale this implementation targets: real Testcontainers integration test proves at-least-once delivery + dedup; local stack is free/FOSS/self-hosted and runs on a single machine. Not load-tested at Growth/Scale volumes — that was never the claim for Phase 1.

The third and fourth prove the FR-7 auth rework end-to-end for real: one changes a password via Keycloak's kc_action=UPDATE_PASSWORD form and confirms the old password is rejected and the new one works at login; the other triggers Keycloak's built-in forgot-password flow, retrieves the real reset email from the local mailpit SMTP catcher via its REST API, follows the reset link, and confirms the new password works — nothing about either flow was taken on faith.

  • Docker Compose — full stack, run for real: built and started every service (docker compose up --build: Mosquitto, TimescaleDB, Keycloak, mailpit, MinIO, backend, fe, and the gateway in --simulate mode) and confirmed, against the live containers: the simulated device's readings flow gateway → Mosquitto → backend → TimescaleDB and are queryable via the REST API; unauthenticated requests are correctly rejected (401); a real browser completing the Authorization Code + PKCE flow against Keycloak gets a token this backend validates correctly, whose subject becomes the claimed device's ownerUserId; the fe container serves the built React app.

    Two real integration snags surfaced and were fixed in the process, both hostname-identity issues inherent to "browser and backend reach Keycloak by different paths" in a docker-compose setup — worth knowing about if this ever gets touched again:

    1. Keycloak's issued token iss claim needs to be one fixed value regardless of whether a request came from the host browser (localhost:8082) or the backend container (keycloak:8080 internally), or Spring Security rejects it as a mismatch. The v3 fix pinned Keycloak's KC_HOSTNAME to host.docker.internal — which worked for that revision's back-channel password-grant login (the browser's fetch() call didn't need to literally resolve that hostname, only the token payload contained it as a string), but broke once real Authorization Code + PKCE login was implemented: Keycloak's login-form action attribute, redirects, and password-reset email links all use KC_HOSTNAME too, and host.docker.internal is not resolvable from the host machine itself (only from inside other containers) — so a real browser (or a person's mail client, for reset links) couldn't actually navigate anywhere Keycloak sent it. Fixed by setting KC_HOSTNAME to plain localhost instead (resolvable by an actual human) and decoupling the backend's own key-fetching from that: it now reaches Keycloak over the compose network directly (thermometer.oidc.jwk-set-uri → keycloak:8080) while still validating the iss claim against the externally-visible localhost:8082 string (SecurityConfig.jwtDecoder, backend/src/main/resources/application-docker.yml) — no single URL has to serve both purposes anymore.
    2. Keycloak's ID token doesn't include realm_access.roles by default (only the access token does — a deliberate OIDC minimality default), but the frontend's role-aware routing derives the signed-in user's role from oidc-client-ts's user.profile, which comes from the ID token. Fixed with a client-level protocol mapper on thermometer-web (realm-export.json) that also includes the realm-roles claim on the ID token.
