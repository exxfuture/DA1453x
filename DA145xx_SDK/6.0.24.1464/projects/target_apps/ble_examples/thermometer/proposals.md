# Proposals — Improvements, Optimizations, New Features

Candidate changes for the thermometer firmware (and, where noted, the Angular
FE in `renesas/thermometer_fe/`). Grounded in the current implementation;
file references point at where each change would land.

Effort scale: **S** (hours), **M** (a day or two), **L** (a week+).

## 1. Power optimizations

### ✅ 1.1 LED duty cycle while advertising — biggest quick win (S)
The LED burns 1–5 mA whenever lit; the current 1 s on / 1 s off blink means a
50 % duty cycle, which dwarfs every other consumer in the system (BLE
advertising averages tens of µA). A 50 ms flash every 2 s (2.5 % duty) is
still clearly visible and cuts LED energy by ~95 %.
*Where:* `led_blink_cb()` in `src/thermometer.c`.

### ✅ 1.2 Slave latency during connection (S)
The connection parameters are 10–20 ms interval with latency 0
(`user_connection_param_conf` in `src/config/user_config.h`), so the radio
wakes up ~50–100×/s just to keep the link alive while measurements happen
every 5 s. Request a longer interval and/or slave latency (e.g. interval
100 ms, latency 4) after service discovery: order-of-magnitude reduction in
connected-mode current, imperceptible latency for this use case.

### ✅ 1.3 Extend the measurement-interval range (S)
`APP_HTPT_VALID_RANGE_MAX` is 60 s. For overnight monitoring 1–5 min
intervals are plenty and proportionally cheaper. Raise the max to 300 s
(`src/config/user_profiles_config.h`); FE already reads the valid-range
descriptor, but verify its input control honors it.

### ⏸ 1.4 Beacon mode: temperature in advertising data (M) — privacy caveats
Broadcast the latest reading in non-connectable advertising (manufacturer
data), letting a gateway/tablet log it with **no connection at all** — lower
power, more robust when the phone wanders off, supports multiple listeners.
Could alternate: connectable advertising when a collector wants control,
beacon otherwise. Pairs with the PACKAGING_CONCEPT.md "peace of mind" flow.
*Where:* new adv-data update via `app_easy_gap_update_adv_data()`; dynamic
advertising data pattern is shown in `Tutorial_SDK` ch. 13.

**Privacy: plaintext beacons are NOT acceptable in clinical settings.** BLE
advertising is cleartext and receivable by any device in radio range; the
packet also carries the (currently fixed, trackable) Bluetooth address and
device name. In a clinic this would leak identifiable patients' temperature
data (HIPAA/GDPR-protected). Required mitigations if this ships:

1. Beacon mode strictly **opt-in** ("home mode", default off); clinical
   deployments remain connection-only over the encrypted link.
2. **Resolvable Private Addresses** (`APP_CFG_HOST_PRIV_RPA` in
   `user_config.h`) so the device cannot be tracked across time.
3. **AES-128-encrypted payload** (DA1453x hardware AES) containing
   temperature + a monotonic counter (replay protection), keyed per-device
   and shared only with the authorized gateway; omit the recognizable device
   name in this mode.

With 2+3 a passive listener learns only that *some* BLE device is present.

### ✅ 1.5 TX power reduction (S)
Full TX power is unnecessary for a bedside range. Dropping a few dB
(`rf_pa_pwr_set()` on DA1453x) trades link margin for battery life; expose as
a config define.

### ✅ 1.6 Production build profile (S)
`CFG_DEVELOPMENT_DEBUG` is defined (README documents it must be undefined for
production). Add `bash build.sh release` that undefines it, disables any
UART console, and asserts watchdog-on-reset behavior — so a production image
is one command, not a manual header edit.

## 2. Reliability / robustness

### ✅ 2.1 I2C bus recovery + sensor soft reset (M)
Today every sensor failure is silently skipped (documented in README
edge-cases). A wedged AHT20 holding SDA low, or a sensor that stops
answering, means **no measurements forever** with no recovery and no signal.
Add a consecutive-failure counter; after N failures issue the AHT20 soft
reset (0xBA), and if the bus itself is stuck, clock SCL manually (GPIO
bit-bang) to release a slave holding SDA.
*Where:* `src/i2c_temp_sensor.c` plus a failure counter in
`src/thermometer.c`.

### ⏸ 2.2 Surface sensor failure over BLE (S–M)
Combine with 2.1: after N consecutive failures, notify the collector (custom
"device status" characteristic, or reuse the Battery Service notification
path) so the FE can show "sensor fault" instead of a silently frozen reading.
For a fever-monitoring product, "no data" must be distinguishable from
"stable temperature".

### ⏸ 2.3 Persist the measurement interval (S)
A collector-configured interval is lost on any reboot (deep-sleep wake,
battery swap). Store it in SPI flash / NVDS and restore in
`user_app_on_init()`.

### ⏸ 2.4 Implement the bond database (M)
All `app_bond_db_callbacks` are NULL, so nothing survives disconnect and the
collector must re-subscribe every time (README edge-case #6). Wiring the
SDK's bond DB (see `ble_app_security` example) gives encrypted reconnects and
CCC persistence — the device resumes indicating automatically on reconnect,
which matters when a phone drops the link overnight.

### ✅ 2.5 Watchdog audit of the ISR-driven measurement chain (S)
The async chain (trigger → timer → read → timer → send) has per-stage guards,
but no end-to-end "measurement completed" watchdog. A cheap invariant: when
`temp_timer_cb` fires, log/count whether the *previous* cycle delivered a
measurement; feeds 2.1/2.2 diagnostics.

## 3. New features

### ⏸ 3.1 Humidity over BLE (M)
Humidity is already measured and discarded (`(void)humi_x100`). Add the
Environmental Sensing Service (Humidity characteristic, UUID 0x2A6F) or pack
it into the beacon payload (1.4). Useful for a nursery: damp/dry air context
next to temperature. FE: one extra characteristic subscription and display.

### ⏸ 3.2 Temperature-threshold alarms in firmware (M)
Let the collector write low/high thresholds (custom characteristic); firmware
raises an alarm indication immediately when crossed, independent of the
regular interval — the "fever alert" feature from PACKAGING_CONCEPT.md. With
1.4, the alarm flag also goes into advertising data so a gateway sees it even
without a connection.

### ⏸ 3.3 Offline measurement buffering (L)
If the collector disconnects (phone rebooted, out of range), measurements are
currently just not taken. Keep measuring while disconnected, store
timestamped readings in a retained-RAM ring buffer (capacity permitting —
`CFG_RET_DATA_SIZE` is 2200 bytes; ~6 bytes/sample buys hours at 1–5 min
intervals), and replay them on reconnect. Turns "gap in the chart" into a
complete night. Requires 2.4 for a smooth resume, and FE work to merge
replayed history.

### ⏸ 3.4 SUOTA — over-the-air firmware update (L)
For the sealed wearable in PACKAGING_CONCEPT.md there is no SWD access in the
field; OTA update becomes essential. The SDK ships the full machinery
(`ble_app_ota` example, secondary bootloader, SUOTA chapters 22–28 in
`Tutorial_SDK`). Costs flash layout changes and ~⅓ of the SPI flash for the
second image slot.

### ✅ 3.5 Median-of-3 sampling + skin-offset calibration (M)
Single samples are exposed to contact noise. Take 3 readings 100 ms apart,
send the median; add a signed offset (custom characteristic, persisted per
2.3) so the FE can calibrate skin-to-core difference against a reference
thermometer. Directly improves the axillary accuracy story.

### ✅ 3.6 Device Information Service with firmware version (S)
`CFG_PRF_DISS` is currently disabled to save memory. Re-evaluate: exposing a
firmware revision string is near-essential once devices are in the field
(and required context for 3.4). Measure the actual RAM cost before deciding.

## 4. Developer experience

### ✅ 4.1 `compile_commands.json` for clangd (S)
Every IDE diagnostic in this project is spurious (missing SDK include paths).
Emit `compile_commands.json` from `build.sh` (the compile commands are
already assembled there) — real diagnostics, working go-to-definition.

### ✅ 4.2 Incremental builds (S)
`build.sh` always rebuilds all 62 files (~documented in README). Adding
`-MMD` dependency files and a timestamp check (or generating a Makefile)
turns the edit-compile loop from ~20 s into ~2 s.

### ✅ 4.3 Host-side unit tests for pure logic (M)
The CRC-8 routine, AHT20 raw-value decode, and IEEE-11073 encoding are pure
functions — extract them into a header testable on the host (the CRC was
already validated this way ad hoc against the CRC-8/NRSC-5 check value).
A `tests/` folder with a `cc`-built runner catches codec regressions without
hardware.

### ✅ 4.4 CI build (S)
A GitHub Actions job installing the ARM toolchain and running `bash build.sh`
(+ 4.3 tests) ensures the repo never contains a non-building firmware state.

## Suggested ordering for the remaining (deferred) work

1. **Confirm the SPI flash part/layout** of the DA14535MOD/devkit — unblocks
   2.3 (interval persistence), 2.4 (bond DB storage), and 3.4 (SUOTA).
2. **Custom GATT service bundle** — one service carrying device status (2.2),
   humidity (3.1), alarm thresholds (3.2), and a runtime calibration-offset
   characteristic (completing 3.5).
3. **3.3 offline buffering** once 2.4 provides reconnect persistence.
4. **3.4 SUOTA** and **1.4 beacon mode** last — both need hardware in hand
   (flash/bootloader work and RF/privacy validation respectively).
