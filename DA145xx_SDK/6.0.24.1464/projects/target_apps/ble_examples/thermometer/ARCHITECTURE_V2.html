Thermometer — System Architecture v2

Revision of ARCHITECTURE.html (v1) after a cost/speed/complexity review. The requirements are unchanged — this document only revisits how they are implemented, trading components that were solving problems the system doesn't have yet for simpler ones, and picking a couple of concrete performance wins.

v1 is not wrong, it's early. Every component v1 proposed is a reasonable choice at real scale. The review below is about sequencing: several pieces (a durable log, a fleet-rollout engine, a device PKI) earn their operational cost only once a specific condition is met. v2 states that condition explicitly and starts simpler until it's hit.
Superseded by ARCHITECTURE_V3.html. v3 keeps every infrastructure decision made here (broker, storage, identity, OTA strategy, deferred-complexity triggers) and swaps the backend implementation language (Go → Java/Spring Boot, matching the team's expertise) and the web frontend framework (Angular → React). This v2 document is kept as the historical record of the cost/complexity review it performed.

1. What changed, and why

Areav1v2WhyWins
Durability layer NATS JetStream, from day one, between broker and ingest workers Cut at MVP/Growth. Ingest worker consumes MQTT directly, QoS 1, acks only after DB commit. Introduce JetStream/Kafka only when a second independent consumer (alerting engine, ML pipeline) needs its own replay cursor on the same messages. QoS 1 + commit-then-ack already gives at-least-once delivery with one consumer. A durable log's value is decoupling multiple consumers — paying for that before it's needed is one more clustered service to run, patch and monitor for zero benefit. simpler cheaper
Live dashboard updates API service relays measurements to browsers over a custom WebSocket Browser/mobile subscribe directly to the MQTT broker over WSS on a per-user scoped topic (live/{user_id}/#); the API issues a short-lived, topic-scoped token, nothing else. Removes a hop and a whole fan-out subsystem from the API service; the broker (already built for millions of subscribers) does the fan-out it's designed for instead of the API server doing it again. faster simpler
API / ingest language "Go/NestJS" — left open Go, decisively, for API and ingest services. Single static binary (trivial container images, fast cold start), low idle memory, and native concurrency that maps cleanly onto MQTT-subscribe/WebSocket-fan-out workloads — meaning smaller instances do more work. cheaper faster
OTA fleet management Eclipse hawkBit from day one (own DB, typically RabbitMQ) DIY: a rollouts/rollout_targets table in the existing Postgres + MinIO for images + simple percentage/group logic in the API service. Adopt hawkBit only when rollout policy genuinely needs its own engine (many concurrent staged rollouts, complex targeting rules, automated abort SLAs across a huge heterogeneous fleet). "Publish an image, target a group, watch the error rate, promote or pause" is ~200 lines of application code before it's a product of its own. Standing up a second stateful service (with its own DB) to do that on day one is disproportionate. simpler cheaper
OTA transfer Full firmware image sent over SUOTA every update Delta/differential images (bsdiff-style binary diff against the device's current version, generated in CI) sent over SUOTA; full image kept as fallback for version jumps too large to diff. Firmware images are typically >90% identical release-to-release. Diffing cuts the bytes transferred over the (slow, power-hungry) BLE link dramatically — shorter update sessions, less battery spent per update, less bandwidth on the collector's connection. faster cheaper
Gateway authentication mTLS client certificates + OIDC client-credentials, as the default Short-lived, device-scoped JWTs (issued by the API, rotated on check-in, verified by the broker's JWT-auth plugin) as the default. mTLS remains available as an optional hardening layer for deployments that specifically require it (e.g. hospital-managed gateway fleets). A private CA plus certificate issuance/rotation/revocation is real, ongoing operational machinery. A rotating signed JWT gives the same practical guarantee (short-lived, revocable, scoped credential) with far less to build and run. simpler
Broker sizing EMQX from day one "for millions of connections" Mosquitto (single node) through the MVP and most of Growth — comfortably handles tens of thousands of concurrent connections on modest hardware. Move to an EMQX (or VerneMQ) cluster when connection count or the need for multi-node HA actually arrives. EMQX's clustering is a real strength — at the scale it's built for. Below that, Mosquitto is lighter, simpler to operate, and just as capable for the connection counts an MVP/Growth fleet will produce. simpler cheaper
Hosting Generic "small VPS" cost sketch, x86 pricing assumed Priced against arm64 instances (e.g. Hetzner's CAX line) — every component here (Go binaries, Postgres, Mosquitto/EMQX, MinIO, Grafana stack) ships arm64 images. Materially cheaper per vCPU/RAM than the equivalent x86 tier, at no functional cost. cheaper
Observability agents Separate Prometheus scrape configs + Promtail as distinct agents Grafana Alloy as the single collection agent (metrics + logs), shipping into the same self-hosted Prometheus/Loki + Grafana backend. One agent to configure and upgrade per host instead of two, same FOSS storage/query backend, no functional loss. simpler
Wire format JSON envelope, unconditionally JSON at MVP/Growth (debuggability matters more than bytes at this volume); switch the envelope encoding to CBOR once message volume is actually large enough for the bandwidth to matter — the JSON Schema still describes the logical shape either way. Saving bytes only pays off once you're moving billions of messages; before that, being able to read a payload with your eyes during debugging is worth more than the bytes saved. honest tradeoff, deferred not forced
Identity provider Keycloak (OIDC) Kept, deliberately. Considered switching to Ory Kratos/Hydra (lighter, Go-based) but decided against it as a default — see the tradeoff note in §8. Keycloak's RAM footprint (a few hundred MB) is not the bottleneck on any VPS tier this system uses; Ory would trade that non-issue for real engineering time building custom login/consent UIs Keycloak ships out of the box. Not every "lighter" component is a net win — this one isn't, yet. no change
Time-series storage PostgreSQL + TimescaleDB Kept. ClickHouse remains the scale-tail escalation option, unchanged from v1. Still the right call: one database for relational + time-series data, SQL throughout, compression and continuous aggregates built in. no change

2. Design principles for v2

  • Earn complexity with a metric, not a forecast. Every "heavy" component (durable log, fleet-rollout engine, clustered broker, device PKI) has an explicit trigger condition in §14 — you introduce it when the metric is hit, not because the architecture diagram eventually needs a box for it.
  • Minimize hops on the hot path. The path that matters for user-perceived speed (device → live dashboard) should touch as few services as possible; every extra hop is added latency and another thing that can queue or fail.
  • One language for the server side. Go throughout the platform's own services keeps operational tooling, deployment and on-call knowledge uniform — a real cost saving that has nothing to do with runtime performance.
  • Prefer deletion over addition when a simpler design covers the same guarantee. Each "cut" in the changelog above still satisfies the original NFR — it just does it with less machinery.

3. Requirements (unchanged)

All functional and non-functional requirements are exactly as defined in ARCHITECTURE.html §1 (FR-1…FR-9, NFR-1…NFR-6) — pushing measurements from device to collector to a customer profile, doctor/admin access, reverse OTA, a cross-platform mobile app plus a Web-Bluetooth web app, extensibility to new measurement types, and the scale/cost/security/ robustness/performance bars. Nothing below changes what the system must do — only how.

5. Device tier

Unchanged from v1: standard GATT services (HTP, Battery, Device Information), no internet credentials on the device, LE Secure Connections pairing already enabled in firmware, bond persistence still tracked as proposal 2.4.

5.1 SUOTA readiness — delta images (new in v2)

The flash layout and signing plan from v1 §4.1 stand (dual-bank rollback, Ed25519 signatures verified by the collector before transfer). v2 adds one step in CI: after building a signed image, also generate a binary diff against the previous released version (bsdiff or a similar block-diff tool) and publish both the full image and the delta to MinIO. The collector fetches the delta whenever the device's current version (read from Device Information Service) has one available, and falls back to the full image for version jumps too large to diff economically (e.g. a device that hasn't been online in a year). This is the single largest lever on update time and on-device power draw during an update, since most of a firmware image doesn't change between releases.

6. Collector tier

The Capacitor recommendation from v1 §5.1 is unchanged and still the core call: one Angular codebase compiled to the web app (Web Bluetooth) and to Android/iOS (native BLE plugin) behind a shared BleTransport interface. Two refinements:

  • Live view without a custom relay. Instead of uploading and then waiting for the API to push a WebSocket update, the web/mobile app that's actively viewing a device's live feed subscribes directly to live/{user_id}/{device_id}/# on the broker over WSS/TLS, using a short-lived, topic-scoped JWT obtained from the API. The upload path and the live-view path are now two independent, simple flows instead of one flow with a fan-out service bolted onto it.
  • Wire format stays JSON for now (see changelog) — CBOR is a drop-in swap on the same schema once the numbers justify it, not a v2 requirement.

Store-and-forward (SQLite/IndexedDB local buffer, idempotent upload keyed on device_id + ts + type) and the optional Raspberry Pi gateway path are unchanged from v1 §5.2–5.3, except gateways now authenticate with a rotating JWT (§8) rather than a client certificate by default.

7.1 Why this is enough

Concernv2 answer
At-least-once delivery MQTT QoS 1 keeps redelivering until acked; the ingest worker acks only after the database transaction commits. A crash mid-processing means redelivery, not loss — exactly the guarantee JetStream would add, without running JetStream.
Dedup Same as v1: (device_id, type, ts) primary key with ON CONFLICT DO NOTHING makes redelivery idempotent.
Backpressure Mosquitto queues QoS 1 messages per client session; the ingest worker's own bounded channel plus Postgres's normal write throughput absorb bursts. At the volumes MVP/Growth actually see (§11) this headroom is ample.
When this stops being enough The moment a second consumer type needs the same measurements independently (e.g. a real-time alerting/rules engine that must replay from an arbitrary point, or an analytics job that shouldn't compete with ingest for the same subscription) — introduce JetStream then, fed by the broker via a bridge, with the ingest worker's own logic (consume → validate → upsert) unchanged.

The message envelope (§6.2 in v1) and storage schema (§6.3 in v1) are unchanged — both already extensibility-ready and don't depend on which durability mechanism sits underneath.

8. Identity, profiles and access control (v2)

Roles, consent-link model, row-level-security enforcement and privacy mechanics are all unchanged from v1 §7. Two v2 refinements:

8.1 Identity provider: Keycloak, kept on purpose

Considered and rejected: switching to Ory Kratos/Hydra. Ory is lighter (Go binaries, tens of MB of RAM) and was tempting to include as a blanket "lighter is cheaper" swap. It isn't a clear win here: Keycloak's RAM footprint (a few hundred MB) is not the constraint on any VPS tier this system uses, while Ory ships no login/consent UI — the team would spend real engineering time building and maintaining self-service flows Keycloak provides out of the box. Optimizing a resource that isn't scarce, at the cost of one that is (developer time), isn't a win. Keycloak stays the default; Ory is worth revisiting only if a future requirement (e.g. an extremely resource-constrained edge deployment) makes Keycloak's footprint the actual bottleneck.

8.2 Gateway authentication: JWT by default, mTLS optional

Gateways register once and receive a short-lived, device-scoped JWT, renewed on check-in via the API (itself authenticated by the previous token plus a long-lived registration secret provisioned at install time). The broker validates the JWT (Mosquitto/EMQX JWT-auth plugin) and its embedded topic claims enforce the same per-device topic ACL as before. This drops the need for a private CA and certificate rotation/revocation tooling for the common case. Deployments that specifically require mutual TLS (e.g. a hospital's own security policy for gateways it manages) can still layer it on — the broker supports both simultaneously — but it's opt-in, not default-on infrastructure everyone pays for.

9. Firmware update pipeline (v2)

Same actors and same safety rails as v1 (signed images, dual-bank rollback, consent before update, phased rollout, per-device status). What changes is who orchestrates it.

Update rollout — DIY orchestration in the platform's own services
1  CI builds thermometer.img ──▶ signs (Ed25519) ──▶ generates delta vs.
   previous version ──▶ publishes full image + delta to MinIO
2  Admin creates a row in `rollouts` (target filter: model, current fw ≤ X;
   group percentages: 1% → 10% → 100%; abort threshold) via the API
3  API evaluates the rollout against `devices` on each collector check-in:
   "does this device have a pending update, and is it in an active group?"
4  Collector (mobile/web/gateway) is told: fetch delta (or full image) from
   MinIO, verify signature + hash
5  Collector connects to the device ──▶ SUOTA transfer into inactive flash
   bank ──▶ device validates CRC ──▶ reboots into new image
6  Collector confirms new version via DIS ──▶ reports status to the API
7  API tallies per-group success/error rate in `rollout_targets`; auto-pauses
   the rollout if the error threshold is exceeded, exposes progress to the
   admin console. Rollback: bootloader falls back to the previous bank on an
   invalid image; a previous version can also be republished as a new rollout.

This is the same functional capability as hawkBit — targeting, phased groups, abort thresholds, per-device status — implemented as two tables and a few endpoints in the platform that already exists, instead of standing up and learning a second product with its own database. See §14 for when to actually adopt hawkBit.

10. Security model (v2)

Hop / layerMechanism
Device ↔ collector (BLE) Unchanged: LE Secure Connections pairing; device holds no internet credentials.
Collector ↔ platform TLS 1.3 everywhere. Users: short-lived OIDC JWTs (Keycloak). Gateways: rotating device-scoped JWTs by default, mTLS optional per-deployment (§8.2). Topic ACLs on the broker pin every client to its own id space either way.
Live feed Browsers/mobile connect directly to the broker over WSS with a short-lived, topic-scoped token minted by the API — scoped to exactly the topics the requesting user/doctor is authorized to read, same authorization model as the REST API, enforced at the broker instead of re-implemented in a relay.
Inside the platform Unchanged: private network between services, secrets in the orchestrator's secret store, least-privilege DB roles.
Data at rest Unchanged: disk/volume encryption, encrypted backups, PII isolated in one table, row-level security as defense in depth.
Firmware Unchanged signing/verification model; delta images are signed and verified the same way as full images (the diff, not just the resulting image, is a signed artifact).
Accountability Unchanged: append-only audit log, retained service logs (now shipped via Grafana Alloy, §13).
Abuse resistance Unchanged: rate limits at the broker and API, schema validation at ingest, dead-letter quarantine for malformed input.

Growth≤ 200k devices~2–8k msg/s Still Mosquitto (single node handles this comfortably) on a larger arm64 box; Go ingest scales to multiple replicas behind the same subscription (shared MQTT session or partitioned by device-id hash); Postgres gains a streaming read replica for dashboard queries.
Scalemillionstens of thousands msg/s Now justified: EMQX (or VerneMQ) cluster for connection fan-in at this size; NATS JetStream (or Kafka/Redpanda) introduced once a second consumer type exists, partitioned by device_id; N ingest workers per consumer group batching inserts; Timescale multi-node or ClickHouse for the analytics tail if the query shape demands it.
  • Same horizontal paths as v1, just introduced later: broker clustering, stream partitioning and stateless replicas are all still in the design — v2 changes when you turn them on, not whether they're available.
  • pgBouncer added at the Growth→Scale transition once concurrent ingest/API replicas make direct Postgres connections the limiting factor — a cheap, standard addition, not a redesign.

12. Extensibility

Unchanged from v1 §11 — the measurement-type registry, GATT-profile pattern on the device, and opaque hawkBit-or-DIY artifact distribution for updates all remain type-agnostic. None of the v2 changes touch this: dropping the durable-log tier and DIY-ing the rollout orchestration are implementation choices behind interfaces that were already type-agnostic in v1.

13. Deployment, operations and cost (v2)

  • Packaging: unchanged — OCI containers, docker-compose for MVP, k3s from Growth on. All images built for arm64.
  • Observability: Grafana Alloy as the single collection agent per host (metrics + logs) shipping into self-hosted Prometheus, Loki and Grafana — same FOSS backend as v1, one agent instead of two.
  • Backups: unchanged — pgBackRest + WAL archiving, MinIO versioned buckets replicated off-site with restic.
  • CI/CD: firmware lane gains one step (generate + sign the delta image alongside the full image); platform lane unchanged.
  • Cost sketch: MVP ≈ one ~€5–8/month arm64 VPS (Hetzner CAX11/CAX21 class) + domain — cheaper than v1's x86 estimate for the same workload, and with one fewer clustered service (no NATS, no hawkBit) to operate. Growth ≈ a couple of larger arm64 nodes + a read replica. Scale ≈ the same handful of dedicated servers as v1 once EMQX/JetStream are actually justified — v2 doesn't change the ceiling, it delays paying for it.
