Thermometer — System Architecture

End-to-end architecture for the BLE thermometer product: embedded sensor → BLE collectors (mobile / web / gateway) → self-hosted data platform → customer, doctor and admin access — with the reverse path used for over-the-air firmware updates. Companion to README.md (firmware), PACKAGING_CONCEPT.md (product concept) and proposals.md (firmware backlog).

Superseded by ARCHITECTURE_V2.html. This v1 document is kept as the historical record of the initial proposal — the current design (same requirements, cheaper/simpler/faster technical choices after a cost/complexity review) lives in ARCHITECTURE_V2.html.

1. Requirements — what we are building

The features below are the product definition. Everything in the architecture sections that follow exists to satisfy one or more of these requirements.

1.1 Functional requirements

IDRequirementDetail
FR-1 Measure temperature on the embedded device The DA14535-based device samples an AHT20 sensor, aggregates samples (median of 3), applies calibration and encodes readings as standard Health Thermometer Profile (HTP) indications. implemented
FR-2 Push measurements to a connected BLE collector Any BLE central that connects and subscribes (enables HTP indications) receives readings at a configurable interval (1–300 s). Collectors can be phones, tablets, laptops or dedicated gateways. implemented
FR-3 Publish measurements to the customer's online profile The collector forwards each reading to the backend, where it is stored against the customer's account and the originating device. Readings taken while offline are buffered on the collector and uploaded later (store-and-forward, no data loss). planned
FR-4 Doctor ↔ patient profile linking A customer can grant a doctor access to their measurements. The link is consent-based, revocable, and audited. A doctor sees the live and historical data of every patient who granted access — and nothing else. planned
FR-5 Admin access Administrators manage the device fleet, user accounts, and firmware releases, and can access measurement data for support/operations under audit. planned
FR-6 Over-the-air firmware updates (reverse flow) An admin publishes a signed firmware image; the backend rolls it out in controlled stages; collectors (mobile app, web app, gateways) download the image and update the embedded device over BLE using SUOTA; update status is reported back per device. Failed updates roll back automatically (dual-image flash). planned
FR-7 Web app for BLE-capable computers Laptops and desktops (macOS, Windows, Linux, ChromeOS) with Bluetooth can connect to the device directly from the browser via Web Bluetooth — no install required. The existing Angular 17 FE (renesas/thermometer_fe/) is the seed of this app. partially implemented (local-only today)
FR-8 Cross-platform mobile app One codebase compiling to both Android and iOS (evaluated in §5). Acts as BLE collector, uploader, live viewer, and SUOTA updater. planned
FR-9 Extensible measurement types Temperature is the first data type, not the only one. The pipeline, storage schema and APIs must accept new measurement types (humidity, heart rate, SpO₂, battery, device diagnostics…) without redesign. planned

1.2 Non-functional requirements

IDRequirementDetail
NFR-1 Scale The pipeline must be designed for millions of devices and their collectors publishing concurrently, and scale down to a single cheap server for early deployments. Horizontal scaling must not require re-architecture.
NFR-2 Free and open-source stack Every server-side component must be free, open-source and self-hostable. No managed cloud services (AWS IoT, Firebase, etc.); no per-message or per-device licensing. Hosting on commodity VPS / bare metal.
NFR-3 Cheap to run An MVP deployment must fit on one small VPS (~€5–15/month). Costs must grow roughly linearly (or better, thanks to compression and batching) with fleet size.
NFR-4 Security & privacy Body-temperature series are health data. TLS everywhere, per-device and per-user credentials, role-based access with least privilege, consent-based sharing, encryption at rest, signed firmware, full audit trail. GDPR-compatible by design (export, erasure, pseudonymization).
NFR-5 Robustness No single lost reading under normal failure modes: collectors buffer offline, the broker persists in-flight messages, the pipeline is at-least-once with idempotent writes (dedup on device_id + timestamp + type). Backpressure instead of collapse under load spikes.
NFR-6 Performance Live readings visible to the customer/doctor within ~1–2 s of measurement when online; dashboard queries over months of history in <1 s (continuous aggregates, not raw scans).

3. System overview

Four tiers. Measurements flow upward (device → collector → platform → people); firmware updates flow downward along the same path. The embedded device only ever speaks BLE; collectors bridge BLE to the internet; the platform is a single self-hosted stack.

Key architectural decisions, justified in the following sections:

  • MQTT at the edge, stream inside. Collectors publish over MQTT (native or WebSocket) — the de-facto IoT protocol with tiny overhead, QoS 1 delivery and broker-side buffering. Inside the platform, messages are bridged into a durable stream (NATS JetStream) that decouples ingestion from processing (NFR-1, NFR-5).
  • One relational database, two workloads. PostgreSQL holds accounts, devices and consent links; the TimescaleDB extension turns the same database into a first-class time-series store (compression, retention, continuous aggregates). One system to operate and back up (NFR-2, NFR-3).
  • Identity is delegated, not hand-rolled. Keycloak issues OIDC tokens for users and (via client-credential grants) for gateways; the API service only verifies and enforces (NFR-4).
  • OTA is a first-class pipeline, not a file download. Eclipse hawkBit manages rollouts (groups, phased deployment, abort, per-device status); collectors are its delivery arm; SUOTA is the last hop (FR-6).
  • Everything runs from one docker-compose on day one and the same images scale out under k3s/Kubernetes later — the architecture does not change, only the replica counts (NFR-1, NFR-3).

4. Device tier — embedded firmware

The firmware is documented in detail in README.md; from the system's point of view the device is deliberately dumb and low-power:

  • Standard GATT services. HTP (0x1809) indications carry IEEE 11073 FLOAT temperatures; Battery Service reports charge; Device Information Service exposes model, application version and SDK version — the version fields are what the update pipeline reads to decide whether a device needs an update.
  • No knowledge of the internet. The device never holds Wi-Fi or cloud credentials; its attack surface is the BLE link only. Timestamps are assigned by the collector at reception (the device has no RTC worth trusting), with the sequence preserved by the 5 s cadence.
  • Pairing. LE Secure Connections (ECDH) pairing is already enabled (CFG_ENABLE_SMP_SECURE). Bond persistence (proposal 2.4) is required before doctor-grade deployments so a reboot does not silently drop encryption.

4.1 SUOTA readiness (firmware work for FR-6)

The SDK ships the complete machinery (the ble_app_ota example, the secondary bootloader project, SUOTA chapters in the Tutorial SDK). The firmware changes, tracked as proposals.md item 3.4:

  1. Flash layout: SPI flash partitioned into product header + two image banks; the secondary bootloader boots the newest valid image and falls back to the other bank if validation fails — this is the rollback guarantee.
  2. SUOTA receiver service (CFG_PRF_SUOTAR) added next to HTP; the collector writes the new image into the inactive bank over GATT, the device validates CRC and reboots into it.
  3. Image signing: images are signed (Ed25519) at build time in CI; collectors verify the signature before transfer, and the version in DIS is compared after reboot to confirm success (the DA14531/35 bootloader itself does not verify signatures — verification lives in the pipeline, §8).

5. Collector tier — mobile, web and gateway apps

Collectors are the bridge: BLE-facing on one side (subscribe to HTP indications, drive SUOTA) and platform-facing on the other (authenticated MQTT/HTTPS). All collectors share the same responsibilities:

  • Scan/connect to DLG_THRM devices, enable indications, decode IEEE 11073, attach a UTC timestamp at reception.
  • Store-and-forward: every reading is written to local storage first (SQLite on mobile/gateway, IndexedDB in the browser), then uploaded and marked acknowledged. Offline operation is therefore free, and uploads are idempotent (device_id + ts + type key) so retries never duplicate (NFR-5).
  • Register/claim devices to the customer's account (first-connect claiming by BD address + proof of physical access, e.g. button press).
  • Act as the SUOTA delivery arm of the update pipeline (§8).

Everything else (decoding, buffering, upload, SUOTA logic, UI) is shared. Flutter is the fallback if native background-collection requirements outgrow what Capacitor's plugin can deliver — the platform-facing protocol (§6) is identical either way.

5.2 Web app (FR-7)

  • The Angular FE evolves into the hosted web app: login (OIDC redirect to Keycloak), live BLE collection via Web Bluetooth, history dashboards from the API, and the browser-side SUOTA updater.
  • Browser support: Web Bluetooth works in Chrome, Edge and other Chromium browsers on macOS, Windows, Linux and ChromeOS (and Chrome on Android). Safari and Firefox do not implement it — on those, the web app still serves dashboards, account, doctor and admin views; only live BLE collection needs Chrome/Edge or the mobile app. Web Bluetooth requires HTTPS, which the deployment provides anyway.
  • Uploads use MQTT-over-WebSocket (EMQX listens on WSS) or plain HTTPS batch POST as fallback — both authenticated with the user's OIDC token.

5.3 Dedicated gateways (optional, unattended sites)

Wards, nursing homes, or households without a resident phone use a headless gateway: a Raspberry Pi (or any Linux SBC) running a small Go/Python service on BlueZ that performs the same collector duties for many devices at once. Gateways authenticate with mTLS client certificates + Keycloak client-credentials, and are the preferred SUOTA arm for mass fleet updates because they don't depend on a user opening an app.

6.1 Why these components

ConcernChoiceRationale (and FOSS status)
Edge protocol MQTT 5 (QoS 1), native + WebSocket Minimal overhead for battery/mobile clients, built-in acknowledged delivery and offline sessions; WSS variant works from browsers. Open standard.
Broker EMQX (Apache-2.0) — or Mosquitto for the MVP single node EMQX clusters horizontally and is benchmarked to millions of concurrent connections; fine-grained ACLs and JWT auth built in. Mosquitto (EPL/EDL) is lighter and perfect until ~100k connections.
Durable stream NATS JetStream (Apache-2.0) Decouples ingestion from processing with replay, consumer groups and exactly-once-per-consumer windows, at a fraction of Kafka's operational weight (single small binary, clusters of 3 for HA). Apache Kafka remains the drop-in alternative if throughput ever demands it — the envelope format doesn't change.
Time-series storage TimescaleDB (Apache-2.0 core) on PostgreSQL Hypertables give ~90%+ native compression on regular telemetry, automatic retention policies, and continuous aggregates for fast dashboards — while staying plain SQL in the same database as profiles and consent links, so access control joins are trivial. (Alternatives: ClickHouse for extreme analytics scale; VictoriaMetrics for metrics-shaped data.)
Live updates to viewers WebSocket/SSE fan-out from the API service Ingest workers publish accepted measurements onto a live.{user_id} subject; the API service forwards to authorized connected dashboards (customer's own page, doctor watching a patient) — NFR-6's 1–2 s freshness.

6.2 Message envelope (FR-9 extensibility)

Every payload — today's temperature and any future type — uses one envelope, so brokers, streams, workers and storage never need to learn new shapes: 

{
  "v": 1,                      // envelope version
  "device_id": "48:23:35:F4:00:10",
  "collector_id": "app-7f3a…", // which phone/browser/gateway relayed it
  "ts": "2026-07-26T12:34:56.789Z",   // collector reception time, UTC
  "type": "temperature",       // measurement type registry key
  "payload": { "celsius": 27.15 },    // type-specific, JSON-schema validated
  "meta": { "fw": "1.4.0", "battery_pct": 87, "rssi": -61 }
}

New types register a name + JSON Schema + storage mapping (§11); unknown types are quarantined to a dead-letter subject, never dropped silently.

6.3 Storage schema (core tables)

users(id, keycloak_sub, display_name, …)
devices(id, bd_addr, model, hw_rev, fw_version, owner_user_id, claimed_at, …)
consent_links(patient_id, doctor_id, scope, granted_at, revoked_at)   -- FR-4
measurement_types(key, json_schema, unit, version)                    -- FR-9
measurements(                                    -- TimescaleDB hypertable
  ts timestamptz, device_id, type, value_num, payload jsonb,
  collector_id, PRIMARY KEY (device_id, type, ts))                    -- dedup
audit_log(actor_id, action, subject, at, detail jsonb)                -- NFR-4
firmware_images(id, version, chip, sha256, signature, minio_url, …)   -- FR-6

value_num carries the primary scalar (fast aggregates); payload keeps the full typed document. Continuous aggregates (min/max/avg per minute/hour/day) back the dashboards; raw rows compress after 7 days and expire per retention policy (configurable per tenant).

7. Identity, profiles and access control

  • Keycloak (Apache-2.0) is the single identity provider. Users (customers, doctors, admins) log in via OIDC from web and mobile; gateways use the client-credentials grant plus mTLS. Tokens are short-lived JWTs carrying realm roles.
  • Roles:
    • customer — full access to own profile, devices and measurements; may grant/revoke doctor links (FR-4); may trigger updates on own devices.
    • doctor — read access to measurements of patients with an active, unrevoked consent_link; may annotate; sees nothing outside the link's scope.
    • admin — user/fleet management, firmware release and rollout control (FR-5, FR-6); data access is break-glass style and always audited.
  • Enforcement lives in the API service and the database, not the client: every query is scoped by the authenticated subject, with PostgreSQL row-level-security policies as a second net (a doctor's session literally cannot select rows of non-consenting patients).
  • Consent is data, not configuration: links carry scope (which measurement types, which time range) and revocation is immediate — the next query and the live feed both respect it.
  • Privacy mechanics (NFR-4): measurement rows reference opaque device/user ids, never names; personal data lives in one small table, which makes GDPR export/erasure a bounded operation (erasure keeps anonymized series if the customer opts in to research use, else cascades).

8. Firmware update pipeline (reverse flow — FR-6)

Updates traverse the same tiers as measurements, downward. The orchestrator is Eclipse hawkBit (EPL — a purpose-built, open-source IoT rollout manager), with MinIO (AGPL) storing the signed images.

Update rollout — admin to device and status back
1  CI builds thermometer.img ──▶ signs (Ed25519, offline key) ──▶ MinIO
2  Admin creates hawkBit rollout: target filter (model, current fw ≤ X),
   groups (canary 1% → 10% → 100%), success/abort thresholds
3  hawkBit assigns the update to each target device
        │
        ▼  collectors learn about it two ways:
   · gateways poll hawkBit DDI API directly (device-management federation)
   · mobile/web apps ask our API "pending update for devices I own?"
     → customer sees a consent prompt (or auto-applies if policy allows)
        │
        ▼
4  Collector downloads image over HTTPS, verifies signature + SHA-256
5  Collector connects to the device ──▶ SUOTA transfer into inactive
   flash bank ──▶ device validates CRC ──▶ reboots into new image
6  Collector reads DIS software-revision ──▶ confirms version
7  Status (success / error + code) reported to hawkBit per device;
   rollout auto-pauses if the error threshold in any group is exceeded
   Rollback: bootloader falls back to the previous bank on invalid image;
   hawkBit can also ship the previous version as a new rollout.
  • Safety rails: phased groups with automatic pause, signature verification before any bytes cross BLE, dual-bank rollback on the device, and a minimum-battery gate checked by the collector before starting a transfer.
  • Consent: customer-owned devices update only after in-app consent (or a customer-enabled auto-update policy); gateway-managed fleets follow the admin's rollout policy.
  • Extensible payloads: hawkBit distributes arbitrary artifacts — the same pipeline later carries configuration bundles or models for other device types (FR-9 symmetry).

9. Security model

Hop / layerMechanism
Device ↔ collector (BLE) LE Secure Connections pairing (ECDH, already enabled in firmware); bond persistence added with proposal 2.4; device holds no internet credentials at all.
Collector ↔ platform TLS 1.3 everywhere (MQTT/TLS, WSS, HTTPS). Users: short-lived OIDC JWTs with refresh. Gateways: mTLS client certificates + client credentials. MQTT topic ACLs pin every client to its own id space — a compromised phone can publish only as itself.
Inside the platform Private network between services (WireGuard/VPC); NATS and Postgres not exposed publicly; secrets in the orchestrator's secret store; per-service least-privilege DB roles.
Data at rest Full-disk / volume encryption (LUKS) + encrypted backups (pgBackRest + restic to off-site storage); PII isolated in one table (§7); row-level security as defense in depth.
Firmware Ed25519-signed images, signature verified by collectors before SUOTA; hash pinned in hawkBit metadata; release keys kept offline; version monotonicity enforced (no silent downgrades outside an explicit rollback rollout).
Accountability Append-only audit_log for logins, consent changes, admin data access, and rollout actions; Loki-retained service logs.
Abuse resistance Per-client rate limits at EMQX and the API gateway; payload JSON-schema validation at ingest; dead-letter quarantine for malformed input — garbage cannot reach storage or dashboards.

10. Scalability and sizing

The load is gentler than it first sounds: a thermometer at a 5 s interval produces 0.2 msg/s while actively collected, and most of a million-device fleet is not connected at any given moment (fever episodes, nightly wear). Design targets:

StageFleetSustained load (est.)Deployment
MVP≤ 5k devices< 200 msg/s 1 small VPS (2 vCPU / 4 GB): docker-compose with Mosquitto, NATS, API, Postgres+Timescale, Keycloak, hawkBit, MinIO, Caddy.
Growth≤ 200k devices~2–8k msg/s 3-node k3s: EMQX replaces Mosquitto, NATS ×3, ingest workers scale by consumer group, Postgres with a streaming replica.
Scalemillionstens of thousands msg/s EMQX cluster (connection fan-in is its benchmarked strength), JetStream or Kafka partitioned by device_id, N ingest workers batching inserts (TimescaleDB sustains 100k+ rows/s on modest hardware with batched writes), Timescale multi-node or ClickHouse for the analytics tail if ever needed.
  • Every horizontal path is already in the design: broker clustering, stream partitioning, stateless API/ingest replicas — scaling is replica counts, not redesign (NFR-1).
  • Batching everywhere: collectors upload buffered readings in batches after offline periods; ingest workers write in batched transactions; compression turns years of per-device history into megabytes (NFR-3).
  • Backpressure by design: spikes (e.g. a flu wave) queue in JetStream, not in the database; collectors additionally hold their local buffer if the broker applies flow control — data is delayed, never lost (NFR-5).

11. Extensibility — beyond temperature (FR-9)

Adding a new measurement type (say, humidity — the AHT20 already measures it — or heart rate from a future device) touches no pipeline plumbing:

  1. Register the type: one row in measurement_types with a JSON Schema and unit; ingest workers hot-load the registry.
  2. Device side: expose it as a standard GATT characteristic (or a custom service for non-standard data) — the SDK's profile machinery is the same pattern as HTP.
  3. Collector side: map the characteristic to the envelope type/payload — one decoder function behind the shared BleTransport interface.
  4. Storage and dashboards: the hypertable and aggregates are type-keyed already; a new dashboard panel selects the new type.

The same symmetry applies downward: hawkBit artifacts are opaque, so new device classes reuse the whole update pipeline with a different last-hop updater. Multi-tenancy (clinics, resellers) is a tenant column + topic prefix already present in the schema and topic scheme.

12. Deployment, operations and cost

  • Packaging: every component ships as an OCI container; one docker-compose.yml for the MVP, the same images under k3s (lightweight Kubernetes) from the growth stage on. Caddy (or Traefik) terminates TLS with automatic Let's Encrypt certificates.
  • Observability: Prometheus (metrics for broker, stream, DB, API), Grafana (ops + optional admin analytics dashboards), Loki (logs), Alertmanager (rollout failures, ingest lag, disk pressure) — all FOSS.
  • Backups: nightly pgBackRest base + WAL archiving; MinIO versioned buckets replicated off-site with restic. Restore drills are part of the runbook, not an afterthought.
  • CI/CD: the existing GitHub Actions workflow grows two lanes: firmware (build, host tests, sign, publish image to MinIO/hawkBit — already half-built today) and platform (build containers, integration tests against a compose stack, deploy).
  • Cost sketch (NFR-3): MVP ≈ one €10/month VPS + domain. Growth ≈ 3 × €20–40 nodes + off-site backup storage. At millions of devices the dominant cost is a handful of dedicated servers (broker + DB + stream), still far below per-message managed-cloud pricing — and with zero license fees by construction (NFR-2).
